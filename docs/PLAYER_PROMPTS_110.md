`Simulation.execute({"type":"SubmitPlayerPrompt", "prompt_type":"DIRECT_ATTENTION", "area_id":"AREA_FRONT_C", "recipient_command_id":"OPERATIONAL_COMMAND"})` accepts exactly those four fields. The only other prompt type is REQUEST_ASSESSMENT. Extra fields (including text, arbitrary metadata, observations, caller IDs/times) fail INVALID_INPUT. The simulation owns timestamps and IDs. Zero-latency receipt ends at PENDING_EVALUATION. It does not create an assessment or information record.

Per the approved amendment, this branch runs before legacy core input allocation/INPUT_RECEIVED/context writes. Its independent player-prompt-input:N counter audits JSON-compatible attempts with command, tick, result and privilege flag in the shared inputs.jsonl array, in actual call order. Invalid structured attempts consume only an audit-input identity, never a prompt/event identity. Non-JSON calls and calls before initialization/after EndRun retain accepted early rejection behavior. The legacy input sequence and core event IDs stay unchanged, including subsequent gameplay inputs.

PlayerPromptService reads existing area/hierarchy associations only at submission. A front area uses its responsible command's ancestry. For frontless areas, every location requires an existing direct-location or owned/direct-stock association within the recipient's descendants or itself. Shared associations suffice; unassociated locations fail. Only enabled OPERATIONAL recipients accept submissions. Scope rejection reasons include UNKNOWN_PROMPT_TYPE, UNKNOWN_STRATEGIC_AREA, DISABLED_STRATEGIC_AREA, UNKNOWN_RECIPIENT_COMMAND, RECIPIENT_NOT_OPERATIONAL, RECIPIENT_DISABLED, AREA_OUTSIDE_COMMAND_SCOPE.

Independent player-prompt:N and player-prompt-event:N counters allocate in successful input order, never sorted by area/type. Two events per success: PLAYER_PROMPT_SUBMITTED, PLAYER_PROMPT_RECEIVED. Each has a previous_prompt_event_id global intent-chain link; received immediately follows its own submitted event. source_input_id links to the independent prompt audit-input ID. The projection's submitted/received event IDs retain explicit lifecycle lineage. No authoritative causation_event_id is overloaded. Events reconstruct the projection through one apply_event writer; replay also regenerates intent from the validated mixed input history to catch forged-but-rehashed events.

`player_prompt_view()` offers detached `current()`, `recent_history(limit=50)`, `status(prompt_id)`, `snapshot()`. Only prompt identity/type/area/recipient/times/state survive the public allowlist. No source metadata, world facts, observer cue or command service is retained. `command_prompt_view(id)` is recipient-scoped and preserves input order. Unknown/LOCAL commands get empty views; other Operational commands see only their own addressed prompts. Held views remain snapshots. Methods return deep copies. These are application access boundaries, not security against arbitrary trusted GDScript access to developer internals.

Packages explicitly include an empty prompt stream when no prompts exist. player_prompt_events.jsonl and final_player_prompts.json (records/player view/recipient views) have fixed manifest filenames, intent schema 2C.2.player-prompt.1 and SHA256 hashes; inputs.jsonl also has a hash. 109 config/events/projection integrity remains intact.
